Lição 0003 • Módulo 1: TypeScript & DTOs

Onde colocar os tipos de respostas aninhadas de APIs no FSD?

🎯 Objetivo da Lição: Entender onde alocar sub-objetos de APIs do mundo real (ex: production_companies dentro de um Movie do TMDB) sem quebrar o isolamento entre entidades no FSD.

1. O Cenário Real (Payloads de API com Objetos Aninhados)

APIs como a do TMDB devolvem dados complexos e aninhados na mesma requisição: 

// GET /movie/11
{
  "id": 11,
  "title": "Star Wars",
  "genres": [{ "id": 12, "name": "Adventure" }],
  "production_companies": [{ "id": 1, "name": "Lucasfilm Ltd.", "logo_path": "..." }]
}

2. A Regra: Evite Importações Cruzadas de Tipos entre Entidades

Tentativa intuitiva mas problemática: 

// ❌ EVITE: entities/movie importando de entities/company
import { Company } from '@/entities/company'; 

export interface Movie {
  id: number;
  production_companies: Company[]; 
}
Por que isso é um problema?
Fatias da mesma camada (entities) não devem importar umas das outras. Isso gera acoplamento oculto e pode disparar erros nos linters do FSD (como o steiger).

3. A Solução: Colocalizar o DTO em entities/movie/model/types.ts

Defina os sub-tipos necessários para representar o contrato da API diretamente dentro do model/types.ts do filme: 

// ✅ RECOMENDADO: src/entities/movie/model/types.ts

export interface MovieProductionCompany {
  id: number;
  logo_path: string | null;
  name: string;
  origin_country: string;
}

export interface MovieGenre {
  id: number;
  name: string;
}

export interface Movie {
  id: number;
  title: string;
  production_companies: MovieProductionCompany[];
  genres: MovieGenre[];
}
