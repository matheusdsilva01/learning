Não transforme o servidor em proxy

Vitória concretaAo final, você conseguirá seguir cada salto de uma URL remota e identificar onde o destino precisa ser validado para impedir SSRF.

Mudança de fronteira

Upload por URL não traz bytes do navegador

No upload multipart, o cliente conecta-se à aplicação e envia bytes. No upload por URL, o cliente fornece um endereço e convence a própria aplicação a iniciar outra conexão.

EntradaQuem busca os bytes?Rede alcançável
Arquivo multipartO cliente envia bytes pela conexão já aceita.A rede entre cliente e aplicação.
URL remotaO servidor resolve o nome e abre uma nova conexão.A rede vista pelo servidor, possivelmente mais privilegiada.

A URL vira uma instrução de rede. O atacante não precisa alcançar diretamente um serviço interno se conseguir fazer o backend requisitá-lo em seu lugar.

No código original

O backend executa duas requisições

  1. ReceberO controller aceita url no corpo.
  2. ClassificarUma string segue para FileUrlService.
  3. VerificarO hostname inicial é testado contra endereços locais.
  4. MedirUm HEAD exige Content-Length.
  5. BuscarUm GET lê os bytes e grava o arquivo.

FileUploadController exige arquivo ou URL, mas não ambos, e envia a origem para processUpload(). Quando a origem é string, FileUrlService.getFile() assume a busca remota.

O recurso pode ser desativado configurando um comprimento máximo de URL não positivo. Quando ativo, o serviço limita o texto da URL, consulta o hostname, executa HEAD, compara o tamanho anunciado, executa GET e aborta se os bytes recebidos ultrapassarem o limite.

Controles diferentes: comprimento da URL e tamanho do corpo limitam recursos consumidos. Eles não determinam se o destino de rede é autorizado.

A ameaça

SSRF explora a posição de rede do servidor

Server-Side Request Forgery ocorre quando uma entrada controlada pelo usuário influencia uma requisição iniciada pelo servidor e permite alcançar um destino que não deveria estar disponível por esse fluxo.

Serviços internos

Painéis, bancos HTTP, sidecars e APIs acessíveis apenas pela rede privada.

Metadados de nuvem

Endpoints link-local podem expor identidade e credenciais da carga de trabalho.

Portas inesperadas

Respostas e tempos podem transformar o backend em instrumento de enumeração.

O impacto não depende de devolver a resposta bruta imediatamente. No WaifuVault, uma resposta GET bem-sucedida pode virar um arquivo hospedado; uma resposta não bem-sucedida tem o corpo lido, registrado e propagado em uma exceção HTTP. Em ambos os casos, alcançar o destino já rompe a fronteira esperada.

Fonte recomendada: OWASP SSRF Prevention Cheat Sheet.

O destino pode mudar

Validar a primeira URL não valida a conexão final

Redirecionamento

URL inicial pública
    └── 302 Location: http://127.0.0.1:3000/admin
            └── cliente HTTP segue e conecta ao destino interno

No snapshot, o hostname inicial passa por isLocalhost(), mas os dois fetch() não desabilitam redirecionamentos. Como o comportamento padrão é segui-los, um novo Location pode trocar host, porta e esquema sem repetir a validação da aplicação.

Resolução DNS

validação: arquivos.exemplo → IP público
conexão:   arquivos.exemplo → IP privado

A dependência resolve o hostname durante a verificação. Depois, fetch() realiza sua própria resolução para conectar. Se as respostas mudarem entre esses momentos, a aplicação validou um endereço e utilizou outro. Essa separação entre verificar e usar é uma forma de time-of-check to time-of-use.

Regra operacional: valide cada salto e garanta que o endereço aprovado seja o endereço efetivamente usado na conexão. Conferir apenas a grafia do hostname não estabelece essa ligação.

Defesa em profundidade

O destino precisa permanecer público até a conexão

CamadaDecisãoLimitação coberta
FuncionalidadeNão oferecer busca remota quando ela não é requisito.Remove toda a superfície de SSRF desse fluxo.
ParserAceitar explicitamente somente http e https; rejeitar credenciais e portas não necessárias.Reduz esquemas e destinos inesperados.
DNS e IPResolver todos os endereços IPv4 e IPv6 e rejeitar qualquer faixa não pública.Bloqueia loopback, privadas, link-local e outras faixas reservadas.
ConexãoVincular o endereço validado à conexão efetiva, preservando hostname para HTTP e TLS.Reduz troca de resposta DNS entre verificação e uso.
RedirectDesabilitar seguimento automático; validar cada Location antes do próximo salto.Impede que uma URL pública redirecione silenciosamente para rede interna.
EgressAplicar firewall ou proxy de saída que negue redes internas e metadata.Continua protegendo quando a validação da aplicação falha.
RecursosLimitar tempo, bytes, redirecionamentos e concorrência.Contém indisponibilidade, mas não substitui autorização do destino.

Se os destinos legítimos forem conhecidos, uma allowlist estrita é preferível. Um host de arquivos genérico, porém, pretende alcançar muitos domínios externos; nesse caso, negar endereços não públicos é necessário, mas a OWASP ressalta que blocklists de aplicação não formam uma barreira perfeita. Controle de egress continua necessário.

Decisão para o primeiro MVP

Upload por URL não é necessário para cumprir a missão inicial de upload privado, TTL, leitura e exclusão. O MVP Laravel aceitará bytes enviados pelo cliente e deixará a busca remota fora do escopo. Isso é redução deliberada de superfície, não uma implementação incompleta de SSRF.

Resumo de bolso

O que precisa permanecer

  • Upload por URL faz o servidor atuar como cliente de rede.
  • SSRF explora a posição e as permissões de rede do backend.
  • Uma URL validada não autoriza automaticamente seus redirecionamentos.
  • Validação DNS precisa permanecer ligada ao endereço realmente conectado.
  • Limites de recursos não substituem autorização de destino.
  • Firewall ou proxy de egress adiciona uma fronteira independente.
  • Remover uma funcionalidade desnecessária pode ser o controle mais confiável.
