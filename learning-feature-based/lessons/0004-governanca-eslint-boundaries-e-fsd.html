Módulo 4 • Governança & FSD

Governança Automatizada, ESLint Boundaries & Feature-Sliced Design

Como blindar a arquitetura contra erosão no CI e quando evoluir para o FSD.

⏱️ Tempo estimado: 8 minutos 🎯 Meta: Configurar enforcement real de limites e comparar Feature-Folders com FSD

1. O Problema da Erosão Arquitetural

Uma arquitetura Feature-Folder perfeita se degrada em semanas sem enforcement automatizado. Desenvolvedores sob pressão de prazo fazem atalhos: deep imports cruzados, lógica de negócio na camada shared/, e componentes de feature acessando internals de outra feature.

A solução é tornar violações arquiteturais em erros de build, exatamente como um erro de tipo do TypeScript. Se o código compilar e o linter passar, a arquitetura está intacta.

3. Configuração Completa do eslint-plugin-boundaries

A configuração abaixo protege as 4 camadas com regras declarativas:

// eslint.config.js (ESLint Flat Config v9+) import boundaries from 'eslint-plugin-boundaries'; export default [ { plugins: { boundaries }, settings: { 'boundaries/elements': [ { type: 'app', pattern: 'src/app/*' }, { type: 'feature', pattern: 'src/features/*' }, { type: 'entity', pattern: 'src/entities/*' }, { type: 'shared', pattern: 'src/shared/*' }, ], 'boundaries/ignore': ['**/*.test.*', '**/*.spec.*'], }, rules: { 'boundaries/element-types': [2, { default: 'disallow', rules: [ // app/ pode importar de qualquer camada abaixo { from: 'app', allow: ['feature', 'entity', 'shared'] }, // features/ consomem entities/ e shared/, nunca app/ { from: 'feature', allow: ['entity', 'shared'] }, // features/ podem importar entre si SOMENTE via Public API { from: 'feature', allow: [['feature', { import: 'index' }]] }, // entities/ só podem importar de shared/ { from: 'entity', allow: ['shared'] }, // shared/ é a fundação — nunca importa de camadas superiores { from: 'shared', allow: ['shared'] }, ], }], // Impõe que imports de features e entities passem pelo index.ts 'boundaries/entry-point': [2, { default: 'disallow', rules: [ { target: 'feature', allow: 'index.(ts|tsx)' }, { target: 'entity', allow: 'index.(ts|tsx)' }, ], }], }, }, ];

4. Dependency Cruiser: Grafo de Dependências & Detecção de Ciclos

Complementa o ESLint com análise estática de grafo e visualização SVG do projeto real:

// .dependency-cruiser.cjs module.exports = { forbidden: [ { name: 'no-circular', severity: 'error', comment: 'Ciclos destroem tree-shaking e causam bugs de inicialização.', from: {}, to: { circular: true }, }, { name: 'no-feature-to-feature-internals', severity: 'error', comment: 'Features não podem importar internals de outra feature.', from: { path: '^src/features/([^/]+)/' }, to: { path: '^src/features/([^/]+)/', pathNot: [ '^src/features/\\\\1/', // Permite import interno da própria feature '^src/features/[^/]+/index\\\\.ts$' // Permite import via Public API ], }, }, { name: 'no-shared-depends-on-features', severity: 'error', comment: 'shared/ NUNCA pode importar de features/.', from: { path: '^src/shared/' }, to: { path: '^src/features/' }, }, ], }; // Comandos de uso: // npx depcruise src --config .dependency-cruiser.cjs --validate # CI check // npx depcruise src --config .dependency-cruiser.cjs --output-type dot | dot -T svg > graph.svg

5. Explorador Interativo: As 6 Camadas do Feature-Sliced Design

Clique em cada camada para entender seu papel, restrições e o que vive dentro dela:

app/ Inicialização, providers, estilos globais e routing
pages/ Composição de widgets e features para formar telas completas
widgets/ Blocos compostos autônomos de UI (Header, Sidebar, ProductGrid)
features/ Ações do usuário com efeito colateral (AddToCart, Login, Search)
entities/ Modelos de negócio e representação visual (Product, User, Order)
shared/ UI Kit, HTTP Client, formatadores, constantes e utilitários puros
👆 Selecione uma camada acima para ver seus segmentos internos, regras de importação e exemplos de código reais.

6. Quando Escalar de Feature-Folders para FSD?

✅ Permaneça com Feature-Folders Pragmático quando:

Time de 2 a 15 devs. Aplicação Next.js ou SPA de médio porte. O overhead de 6 camadas formais não compensa. O eslint-plugin-boundaries já garante integridade suficiente.

⚠️ Considere migrar para FSD quando:

Time acima de 20 devs trabalhando no mesmo repositório. Necessidade formal de distinguir entre ações do usuário (features/) e representação de entidades (entities/). Múltiplos squads precisam de contratos rígidos entre camadas com linter oficial (steiger).

❌ NÃO migre para FSD quando:

Projeto está em fase de MVP ou protótipo. Time não tem disposição para estudar a especificação formal. Aplicação possui menos de 5 features de negócio. O custo de boilerplate das 6 camadas seria maior do que o benefício de governança.
