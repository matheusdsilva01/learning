Cheat Sheet #001

Arquitetura Feature-Folder: Guia Canônico

Regras de decisão, limites de importação, anatomia interna e anti-padrões.

1. Árvore de Decisão: "Onde devo salvar este arquivo?"

❓ Você está criando um novo arquivo (componente, hook, tipo, api)? │ ├──► Este código é exclusivo de uma regra de negócio específica? │ │ │ ├── SIM ──► Salve dentro de `src/features//` │ │ ├── Chamadas de API / Queries ──► `api/` │ │ ├── Componentes visuais ──► `components/` │ │ ├── Hooks de estado local ──► `hooks/` │ │ ├── Store (Zustand/Context) ──► `stores/` │ │ └── Contratos TypeScript ──► `types/` │ │ │ └── NÃO ──► Mais de 2 features distintas utilizam esse código? │ │ │ ├── SIM ──► É um componente genérico de UI (botão, input, modal)? │ │ ├── SIM ──► `src/components/` ou `src/shared/ui/` │ │ └── NÃO ──► É utilitário / cliente HTTP? │ │ ├── SIM ──► `src/lib/` ou `src/shared/utils/` │ │ └── NÃO (É entidade de domínio) ──► `src/entities/` │ │ │ └── NÃO ──► Se apenas 1 feature o utiliza hoje, MANTENHA na feature!

2. Anatomia Canônica de uma Feature

src/features/cart/ ├── api/ # Queries e Mutations (TanStack Query), fetchers │ ├── get-cart.ts │ └── add-to-cart.ts ├── components/ # Componentes privados da feature │ ├── cart-drawer.tsx │ ├── cart-item.tsx │ └── cart-summary.tsx ├── hooks/ # Custom hooks internos de comportamento │ └── use-cart-drawer.ts ├── stores/ # Estado da feature (Zustand slice ou Context) │ └── cart-store.ts ├── types/ # Tipagens TypeScript internas │ └── index.ts └── index.ts # ⚠️ PUBLIC API ÚNICA (Barreira de Encapsulamento)

3. Matriz de Permissão de Imports

Origem (Quem importa) Destino (O que está sendo importado) Status Justificativa Arquitetural
src/app/ ou src/pages/ @features/cart (via index.ts) PERMITIDO Thin routes apenas montam e orquestram features públicas.
src/features/checkout/ @features/cart (via index.ts) PERMITIDO Consumo de API pública explícita entre features.
src/features/checkout/ @features/cart/components/cart-item PROIBIDO Deep import quebra o encapsulamento interno da feature.
src/features/* @shared/* ou @components/* PERMITIDO Features podem consumir livremente a camada base compartilhada.
src/shared/* @features/* PROIBIDO Inversão de dependência: a base compartilhada nunca conhece features.
src/features/cart/ src/features/cart/components/* PERMITIDO Imports relativos internos dentro da mesma feature são livres.

4. Como Definir uma Feature (Os 3 Testes Ácidos)

Teste Pergunta Prática Critério de Aprovação
1. Teste da Deleção "Se eu apagar a pasta da feature, o restante do app compila sem erros ocultos?" SIM → É uma Feature. Zero código órfão deixado para trás.
2. Teste do Verbo "Representa uma capacidade/ação funcional de negócio do usuário?" SIM → Ação = Feature (`cart`, `checkout`). Substantivo puro = Entity (`Product`, `User`).
3. Teste da Regra Própria "Possui chamadas de API, validações e mutations exclusivas desse fluxo?" SIM → Feature (`src/features/*`). Se for UI sem regra de negócio → `src/shared/ui/`.
A Regra da Evolução em Duas Fases (Exemplo do Cupom)

Fase 1 (Simplicidade): O cupom é apenas um input no carrinho que faz POST /api/cart/coupon. Ele vive 100% dentro de src/features/cart/. As validações de negócio pertencem 100% ao backend.
Fase 2 (Promoção a Domínio): Se o negócio criar tela de Carteira no Perfil e Checkout 1-Clique, o cupom é promovido para src/features/coupons/ e exporta CouponWallet, CouponInput e CouponSelector.

6. O Teste da Deleção e o Blast Radius (Raio de Explosão)

O teste de deleção não é sobre "apagar e nada quebrar como mágica", mas sim ter previsibilidade total do que vai quebrar:

Garantias do Blast Radius em Feature-Folders

1. Zero Código Órfão: 100% dos hooks, componentes, testes e queries morrem juntos na pasta.
2. Erros Finos e Previsíveis: O TypeScript acusa erro apenas nas 1 ou 2 linhas onde a Public API foi consumida.
3. Limpeza em 1 Minuto: Você apaga as linhas apontadas pelo compilador e a base está limpa.

7. Migração de Legados: Padrão Strangler Fig (Estrangulamento)

Como migrar sem parar o time

1. Novas Features: Toda feature nova já nasce obrigatoriamente em src/features/<nome>/.
2. Regra do Escoteiro: Só migre código legado de src/components/ quando precisar alterar a regra de negócio dele.
3. Esvaziamento Natural: Com o tempo, a pasta legada esvazia e sobram apenas primitivos puros de UI.

8. Guia Rápido de Nomenclatura: Auth, User, Dashboard & Settings

Nome Proposto Classificação Onde Deve Ficar Racional
Auth FEATURE src/features/auth/ Domínio fechado (login, cadastro, recuperação, sessão).
User ENTITY / FEATURE entities/user ou features/profile Dados transversais/avatar = Entity. Edição de dados do usuário = Feature (`profile`). Gestão de membros = `user-management`.
Dashboard ROTA / PÁGINA src/app/(dashboard)/page.tsx Dashboard é uma tela orquestradora que compõe widgets de múltiplas features. Não é um domínio isolado.
Settings ROTAS AGREGADORAS src/app/settings/*/page.tsx Dividir em sub-rotas consumindo suas respectivas features (`settings/billing` consome `features/billing`).
