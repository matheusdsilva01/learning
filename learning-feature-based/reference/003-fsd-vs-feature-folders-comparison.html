Referência Técnica #004

Feature-Folders Pragmático vs Feature-Sliced Design (FSD)

Comparativo estrutural, regras de camadas, cenários de adoção e configuração real de ESLint Boundaries.

1. Hierarquia de Camadas do FSD

O Feature-Sliced Design formaliza 6 camadas com direção estrita de dependência (de cima para baixo):

┌─────────────────────────────────────────────────────────────────────────────────┐ │ CAMADA 1: app/ Inicialização, providers globais, routing, estilos globais │ │ Só existe UMA instância. Importa qualquer camada abaixo. │ ├─────────────────────────────────────────────────────────────────────────────────┤ │ CAMADA 2: pages/ Composição de widgets e features para formar telas │ │ Equivalente ao Next.js app/page.tsx + layout.tsx │ ├─────────────────────────────────────────────────────────────────────────────────┤ │ CAMADA 3: widgets/ Blocos compostos autônomos de UI (Header, Sidebar, Footer) │ │ Montam features e entities dentro deles. │ ├─────────────────────────────────────────────────────────────────────────────────┤ │ CAMADA 4: features/ Ações do usuário com efeito colateral │ │ Ex: AddToCart, Login, SearchProducts, PlaceOrder │ ├─────────────────────────────────────────────────────────────────────────────────┤ │ CAMADA 5: entities/ Modelos de negócio e representação visual canônica │ │ Ex: Product (card, model, API), User, Order │ ├─────────────────────────────────────────────────────────────────────────────────┤ │ CAMADA 6: shared/ Utilitários agnósticos de negócio │ │ UI Kit, HTTP Client, formatadores, constantes │ └─────────────────────────────────────────────────────────────────────────────────┘ Regra de Ouro do FSD: ► Uma camada SÓ pode importar de camadas ABAIXO dela. NUNCA de cima ou da mesma camada. ► features/ PODE importar de entities/ e shared/. Mas NUNCA de pages/ ou widgets/.

2. Feature-Folders Pragmático vs FSD: Mapeamento Estrutural

Aspecto Feature-Folders Pragmático Feature-Sliced Design (FSD)
Número de Camadas 3 camadas flexíveis:
app/routes, features, shared		 6 camadas estritas:
app pages widgets features entities shared
Definição de "Feature" Módulo de domínio completo (ex: cart/ contém UI, API, hooks, store, testes) Apenas a ação do usuário com efeito colateral. A representação visual do modelo vive em entities/
Onde ficam ProductCard, UserAvatar? features/catalog/components/ entities/product/ui/ (card e modelo ficam juntos na entidade)
Onde ficam Header, Sidebar? src/components/ (shared UI) widgets/header/, widgets/sidebar/ (camada própria)
Comunicação entre features Public API (index.ts) + Slots + Event Bus + Cross-Feature Selectors Estritamente via composição em pages/ e widgets/. Features NUNCA se importam entre si
Segmentos Internos Convenção livre: api/, components/, hooks/ Padronizados: ui/, model/, api/, lib/, config/
Enforcement eslint-plugin-boundaries + convenção do time @feature-sliced/eslint-config + steiger (linter oficial FSD)
Curva de Adoção Baixa-Média. Um README de 1 página é suficiente para onboarding. Alta. Exige estudo formal da especificação e treinamento do time.
Cenário Ideal Times de 2-15 devs. SPAs e apps Next.js médios. Monorepos corporativos com 20+ devs e múltiplos squads.
Risco Principal Erosão arquitetural se linting não for configurado. Overengineering e boilerplate excessivo em projetos menores.

3. Configuração Real: eslint-plugin-boundaries

// eslint.config.js (Flat Config ESLint v9+)
import boundaries from 'eslint-plugin-boundaries';

export default [
  {
    plugins: { boundaries },
    settings: {
      'boundaries/elements': [
        { type: 'app',      pattern: 'src/app/*' },
        { type: 'feature',  pattern: 'src/features/*' },
        { type: 'entity',   pattern: 'src/entities/*' },
        { type: 'shared',   pattern: 'src/shared/*' },
      ],
      'boundaries/ignore': ['**/*.test.*', '**/*.spec.*'],
    },
    rules: {
      'boundaries/element-types': [2, {
        default: 'disallow',
        rules: [
          // app/ pode importar de qualquer camada
          { from: 'app', allow: ['feature', 'entity', 'shared'] },

          // features/ podem importar de entities/ e shared/
          { from: 'feature', allow: ['entity', 'shared'] },

          // features/ podem importar entre si SOMENTE via Public API (index.ts)
          { from: 'feature', allow: [['feature', { import: 'index' }]] },

          // entities/ só podem importar de shared/
          { from: 'entity', allow: ['shared'] },

          // shared/ é a base — não pode importar de cima
          { from: 'shared', allow: ['shared'] },
        ],
      }],

      // Proíbe deep imports dentro de features (impõe uso de index.ts)
      'boundaries/entry-point': [2, {
        default: 'disallow',
        rules: [
          { target: 'feature', allow: 'index.(ts|tsx)' },
          { target: 'entity',  allow: 'index.(ts|tsx)' },
        ],
      }],
    },
  },
];

4. Configuração Real: Dependency Cruiser

// .dependency-cruiser.cjs
module.exports = {
  forbidden: [
    {
      name: 'no-circular',
      severity: 'error',
      comment: 'Dependências circulares destroem tree-shaking e causam bugs de inicialização.',
      from: {},
      to: { circular: true },
    },
    {
      name: 'no-feature-to-feature-internals',
      severity: 'error',
      comment: 'Features não podem importar arquivos internos de outras features.',
      from: { path: '^src/features/([^/]+)/' },
      to: {
        path: '^src/features/([^/]+)/',
        pathNot: ['^src/features/\\1/', '^src/features/[^/]+/index\\.ts$'],
      },
    },
    {
      name: 'no-shared-depends-on-features',
      severity: 'error',
      comment: 'A camada shared/ nunca pode importar da camada features/.',
      from: { path: '^src/shared/' },
      to: { path: '^src/features/' },
    },
  ],
};
