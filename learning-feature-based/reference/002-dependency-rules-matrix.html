Referência Técnica #002

Matriz de Dependências & Comunicação Inter-Feature

Grafo Acíclico (DAG), Inversão de Controle, Composição por Slots e Padrão Thin Routes.

1. Grafo Acíclico Direcionado (DAG) de Dependências

Em uma arquitetura de frontend escalável, as dependências devem fluir estritamente de cima para baixo. Nenhuma dependência circular ou horizontal cruzada profunda é permitida:

┌─────────────────────────────────────────────────────────────────────────────┐ │ CAMADA 1: APP & ROTAS │ │ (Next.js app/**/page.tsx, layout.tsx, router controllers) │ └──────────────────────────────────────┬──────────────────────────────────────┘ │ (1) Orquestra e injeta slots ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ CAMADA 2: FEATURES (MODULARES) │ │ │ │ ┌───────────────────────┐ ┌────────────────────────┐ │ │ │ src/features/catalog │ │ src/features/cart │ │ │ │ (Cards, Filtros, │ │ (Drawer, Items, │ │ │ │ useProducts) │ │ useCartSummary) │ │ │ └───────────┬───────────┘ └───────────┬────────────┘ │ │ │ │ │ │ │ (X) PROIBIDO: Dependência direta │ │ │ │ entre features com regras cruzadas │ │ │ └──────────────────────(X)───────────────────┘ │ └──────────────────────────────────────┬──────────────────────────────────────┘ │ (2) Consomem modelos e utilitários ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ CAMADA 3: DOMÍNIO TRANSVERSAL (ENTITIES) │ │ src/entities/product, src/entities/user, src/entities/cart │ │ (Modelos TypeScript puros, Schemas Zod, Parsers) │ └──────────────────────────────────────┬──────────────────────────────────────┘ │ (3) Consomem infraestrutura pura ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ CAMADA 4: SHARED / CORE / DESIGN SYSTEM │ │ src/shared/ui (Button, Modal), src/shared/lib (HttpClient) │ └─────────────────────────────────────────────────────────────────────────────┘

2. Os 4 Padrões de Comunicação Inter-Feature

Padrão 1: Inversão de Controle com Slots (Slot Pattern)

Cenário: O cartão de produto (catalog) precisa exibir um botão "Adicionar ao Carrinho" (cart).

❌ Acoplamento Direto (Antipadrão)

// src/features/catalog/components/product-card.tsx
// Violação: catalog depende diretamente de cart!
import { AddToCartButton } from '@/features/cart';

export function ProductCard({ product }: Props) {
  return (
    <div className="card">
      <h3>{product.name}</h3>
      <AddToCartButton productId={product.id} />
    </div>
  );
}

✅ Desacoplamento por Slot (Recomendado)

// src/features/catalog/components/product-card.tsx
// Catalog desconhece a existência do carrinho!
interface ProductCardProps {
  product: Product;
  actionSlot?: React.ReactNode;
}

export function ProductCard({ product, actionSlot }: ProductCardProps) {
  return (
    <div className="card">
      <h3>{product.name}</h3>
      {actionSlot}
    </div>
  );
}

Padrão 2: Camada de Entidades Compartilhadas (Shared Entities)

Cenário: As features catalog, cart e checkout precisam manipular o mesmo modelo Product.

// src/entities/product/types.ts
export interface Product {
  id: string;
  sku: string;
  name: string;
  priceInCents: number;
  currency: 'BRL' | 'USD';
  stockQuantity: number;
}

// Tanto features/catalog quanto features/cart importam de @entities/product
import type { Product } from '@/entities/product';

Padrão 3: Event-Driven / Pub-Sub Desacoplado

Cenário: Ao finalizar a compra em checkout, as notificações devem exibir um toast de sucesso e o carrinho deve ser limpo, sem que checkout importe notifications.

// src/shared/lib/events.ts
import mitt from 'mitt';

type AppEvents = {
  'order:placed': { orderId: string; totalInCents: number };
  'cart:item-added': { productId: string; quantity: number };
};

export const eventBus = mitt<AppEvents>();

// Na feature checkout (Emissor):
eventBus.emit('order:placed', { orderId: 'ord_123', totalInCents: 4990 });

// Na feature notifications (Ouvinte desacoplado):
eventBus.on('order:placed', ({ orderId }) => {
  toast.success(`Pedido #${orderId} confirmado com sucesso!`);
});

Padrão 4: Cross-Feature Selectors (Leitura Pública de Estado)

Cenário: A feature checkout precisa saber quantos itens existem no carrinho.

// src/features/cart/index.ts (Public API)
export { useCartSummary } from './hooks/use-cart-summary';
export { useCartCount } from './stores/cart-store';

// src/features/checkout/components/checkout-header.tsx
// ✅ Permitido: importando selector explícito da Public API oficial
import { useCartSummary } from '@/features/cart';

3. Thin Routes vs Colocation no Next.js App Router

Aspecto Thin Routes (Recomendado) Colocation Radical
Estrutura de Pastas src/app/(shop)/checkout/page.tsx apenas importa @features/checkout Páginas inteiras residem dentro de src/features/checkout/routes/
Vantagem Clara separação entre framework (rotas/layouts) e lógica de negócio. Facilita migração de frameworks. Máxima proximidade de arquivos relacionados à rota.
Desvantagem Camada fina extra de arquivo page.tsx por rota. Acoplamento com as convenções de roteamento do framework dentro das features.
Papel do page.tsx Extrai params, invoca Server Actions/Features e injeta Slots de composição. Apenas re-exporta a página interna da feature.

4. Como Evitar o Código Kamehameha (Slot Hell no JSX)

Quando a composição por slots é usada em excesso na page.tsx, a indentação do JSX forma uma pirâmide profunda (>>>>>>>>). Utilize as estratégias abaixo para manter o código plano:

❌ Pirâmide de Slots (Kamehameha)

// page.tsx com slots excessivos
<PageLayout
  header={
    <Header
      actions={
        <CartBadge
          dropdown={
            <CartDropdown
              checkout={<CheckoutBtn />}
            />
          }
        />
      }
    />
  }
/>

✅ Compound Components ou Widgets

// page.tsx plana e declarativa
<ShopHeader />
<CatalogProductGrid />

// Ou usando Compound Components:
<ProductCard product={item}>
  <ProductCard.Image />
  <ProductCard.Title />
  <ProductCard.Actions>
    <AddToCartButton productId={item.id} />
  </ProductCard.Actions>
</ProductCard>
